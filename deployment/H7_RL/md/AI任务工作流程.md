# AI任务工作流程

制定日期：2026-11-04。依据用户与AI逐例讨论后确认的协作方式制定。

## 0. 每次任务开始的强制阅读要求

**本文件是重要的必读工作规范，不是可选参考资料。每次开始新的任务，包括同一聊天中的新任务，都必须先读取当前版本，再进行任务分类、调查、方案设计或修改。** 不得仅凭旧聊天、记忆或以前读过的印象跳过阅读；同一任务的连续执行无需每一步重复读取，文件更新或上下文恢复后应重新读取。

固定阅读顺序：本文件 → 当前工程的协作规范 → 当前工程总览 → 与本任务直接相关的资料。用户最新明确要求优先，工程物理标定、Git及验证红线仍须遵守。无需每次机械复述全文，但实际行为必须执行本流程。

## 1. 适用范围与职责

本文件是本工作区各类AI任务的共享协作流程。每次任务按同一套判断规则执行，不随意改变确认方式。具体工程的物理标定、代码、Git及验证约束仍须遵守；用户最新明确要求优先。

- 用户决定目标、重要取舍、授权范围及实际需求是否满足。
- AI负责调查现状、补全方案与验收建议、执行已授权工作、提供验证证据，并指出需要用户决定的问题。
- 用户可以用自然语言提出需求，不必自行填写完整规格。AI先整理理解，仅对会影响结果的歧义提问。
- 讨论、建议、用户确认、实际实施和验证结果必须区分，不把讨论过的内容视为已经批准或完成。

## 2. 任务判断与确认方式

任务体量越大、复杂度越高，执行前和执行中的对齐越充分。同时考虑目标清晰度、影响范围、不确定性、控制行为和操作后果，不能只看修改行数。

| 任务类型 | 默认执行方式 | 确认节点 |
| --- | --- | --- |
| 简单明确的局部任务，如补注释、文字修订 | 自行检查、执行、验证并报告 | 出现关键歧义或范围扩大时 |
| 整理、重构、调整函数或接口用法 | 先展示旧 → 新的变化与检查方法 | 用户确认方案后修改 |
| 故障排查 | 先提出方向、依据和优先级，与用户历史经验对齐 | 展开排查前；后续改变关键方向或需要修改时 |
| 新功能、跨模块等大任务 | 调查现状、网上研究、比较方案，逐步细化并拆分 | 选择方案、重要细节及影响整体结果的阶段节点 |
| Git任务 | 使用现有 `/git` skill，遵守实际仓库约定 | 按skill与项目授权要求执行 |

任务分类可以在调查后调整。发现任务比预期复杂时，说明新增影响，只对新增范围或重要决策取得确认；已明确授权的常规步骤不重复询问。

进度告知不等于决策确认。普通进度更新后继续工作；确实需要用户决定时，明确指出待决定项，并等待相关答复。未收到回复不能视为批准，可继续不依赖该决定的工作。

## 3. 明确目标、范围和完成标准

开始时由AI按实际需要整理以下内容。简单任务用一两句话说明，复杂任务再展开，不强制每次输出完整表格。

| 项目 | 必须明确的内容 |
| --- | --- |
| 目标 | 希望最终得到什么结果，或改变什么现象 |
| 范围 | 本次处理的对象、相关文件或模块，以及必要边界 |
| 交付物 | 分析结论、候选方案、代码差异、文档或其他具体结果 |
| 验收方法 | 用什么证据判断完成，哪些结果需要外部或实机验证 |
| 执行方式 | AI可自主推进到哪里，哪些决策需要用户参与 |

需求模糊时，先给出AI的理解与推荐交付物，请用户纠正关键偏差。会改变目标、控制行为或验收结论的未知项不能擅自假设。

## 4. 各类任务的固定流程

### 4.1 简单明确的任务

阅读必要上下文 → 完成局部修改 → 检查实际差异 → 报告结果。

例如补充函数注释，可以直接执行。发现疑似bug时单独说明，不顺手修改逻辑，不扩展成模块重构。

### 4.2 整理、重构和用法调整

**这类任务不允许改变控制效果。** 仅处理效率、可读性、代码组织、接口用法、函数选用等内容。控制效果变更必须另行明确讨论和授权，不能夹带在整理中。

执行前先阅读现状，简短说明：

1. 当前是什么样，准备从什么改成什么。
2. 拟修改哪些文件、函数和必要的配套头文件。
3. 修改理由，以及如何检查控制行为保持一致。

用户确认后再修改；用户已经明确批准具体方案时直接执行，不重复确认。

行为一致性需要核对实际语义，包括公式、计算顺序、浮点精度、单位、状态历史、初始化与退出、边界处理、限幅、调用顺序及周期。替换函数、减少运算或调整接口不能仅凭名称相似就认定等价。

如果发现整理方案可能改变输出、时序或控制效果，暂停相关修改，解释具体差异并重新讨论。没有测量，不宣称执行耗时已经下降；检查不足，不保证实机效果完全一致。

执行前说明示例：

> 拟将A.c中三处重复计算提取为公共函数，并同步A.h声明；现有公式、状态、调用顺序和限幅保持一致。先展示关键旧 → 新代码，确认后修改。

### 4.3 故障排查

先交流排查方向 → 用户补充历史经验 → 调整优先级 → 收集证据 → 缩小原因 → 提出修正 → 按授权修改与验证。

展开排查前，先简短说明：

- 已知现象和已有证据。
- 优先检查哪些方向，各自的依据。
- 哪些方向暂时靠后，以及排查准备得到什么证据。

给用户机会补充哪些查过、如何排除、哪些尚未检查，再按对齐后的顺序展开。为提出方向所需的必要只读了解可以先做，不能先大范围排查一遍再通知用户。

对已有排除结论优先复用。只有出现新证据、条件变化或原验证不足时才重新检查，并说明理由。不为了凑排查清单重复低优先级检查。

控制、极性、零位等疑点按工程边界处理，不以猜测修改来试错。需要实机数据时，给出具体采集方法和判断标准；本工作区嵌入式项目默认使用VOFA及导出CSV，说明零基通道、单位和采集步骤，不默认索取Watch值。

### 4.4 大任务与新功能

调查现状及硬件 → 网上研究 → 比较候选方案 → 用户选择方向 → 逐步补细节和验收标准 → 拆成小任务 → 分阶段实施与验证。

1. 先核对当前项目和硬件条件，区分已知事实与待确认信息。
2. 网上研究优先关注RoboMaster论坛：https://bbs.robomaster.com/ ，结合必要的官方资料、论文和原始项目。论坛贴合比赛场景，但帖子中的条件和结论仍须核对，不能直接当成本机适用事实。
3. 给出有实质区别的候选方案，比较适用场景、硬件要求、实现代价、局限和验证方式，并附来源。说明当前最推荐哪个、为什么适合现有方案与硬件；未知条件明确标出。
4. 用户选择方向后，再一点一点补充相关细节与标准。优先询问会影响架构或后续实施的决策，不一次性让用户回答全部实现细节。
5. 将选定方案拆成可独立检查的小任务。每个小任务写清目标、范围、前置条件、交付物、验收方法和待确认项，并按本文件对应任务类型执行。
6. 只有关键选择变化、阶段结果影响后续方案或发现新约束时再对齐，不对每个常规实现步骤设置确认点。

研究和选择方案不代表已授权整体实施。用户明确选择某阶段实施后，在该范围内推进。

### 4.5 Git任务

沿用现有 `/git` skill及实际仓库规范，核对差异、提交范围、中文提交信息、验证证据与操作授权。本文件不复制另一套Git流程，不因任务规模小而跳过既有约定。

## 5. 执行中出现问题

- 普通工具或路径错误：自行修正，继续已授权工作。
- 验证失败：说明实际失败，定位原因，优先修复本次修改引入的问题；不为通过检查擅自降低验收标准。
- 同一方法反复失败且没有新证据：停止机械重复，整理已知事实和已排除项，调整方法；关键路径改变时与用户对齐。
- 缺少关键数据：明确缺什么、影响什么、如何获取，继续不依赖该数据的部分。
- 发现范围外问题：说明与当前目标的关系；需要扩大范围时，提出具体建议等待决定，不顺手处理。
- 发现方案无法满足目标或硬件条件：保留已完成成果，说明差距、替代方案及代价，回到相应决策点。

需要用户决定时，给出“事实与证据、待决定项、可选做法、推荐及影响”，不只说“遇到问题，请确认”。

## 6. 安全与授权边界

- 阅读和分析不自动授予代码、配置或控制行为修改权限；具体按任务类型及工程规范执行。
- 保留用户已有修改，不自行覆盖、清空或回退无关工作。需要撤销时只处理有明确归属和授权的内容。
- 不擅自修改物理极性、零点、轴向、MIT量程等标定，具体执行工程红线。
- 对外发送、上传或公开资料、发布、付费、设备操作及难以撤销的操作，先核对明确授权。授权已有覆盖时不重复询问，新增影响不能从普通代码修改要求中推定。
- 文档约定不等于工具权限隔离。有实际隔离需求时，另行明确访问范围、备份或恢复措施，不把文字规则描述为技术上无法越界。

## 7. 验证、交付与后续维护

验证规模与改动匹配。纯文档检查差异、引用和规则一致性；代码检查按实际修改及项目要求执行，不为简单任务附加无关构建或大规模测试。

交付简明说明：

1. 做了什么，修改哪些文件及关键函数；必要时展示实际差异。
2. 做过什么验证，结果及证据是什么。
3. 哪些部分尚未完成或仍待实机、外部条件验证。
4. 如有后续步骤，明确由谁做、需要什么输入或决定。

“代码已修改”“编译通过”“软件检查通过”“实机效果确认”分别报告，不能互相替代。未完成就明确标注，不用含糊结论掩盖缺口。

新任务重新判断类型，但保持本文件的判定标准。工作中发现规则缺口时提出具体调整建议，经用户要求后更新正文；不因单次意外自行增加永久关卡，也不重复创建同类流程文档。
