# H7控制链路延迟测量：交付、示例方案与验收

日期：2026-11-02。状态：**测量方案与交付规范，尚未执行本次硬件测试。**

目标是交付一套别人能复算、能按同样流程重新测量的数据，而不只是“延迟大约几毫秒”。本文中的时长、样本数、仪器设置和限值示例均须结合实际设备验证；**示例不是实测值，也不是新的电流、力矩或仿真参数授权。**

本文件只安排测量与验收，不改变机器人极性、零点、PD参数、模型权重或安全保护，不授权烧录、使能电机或训练。硬件操作由实际H7负责人按确认后的台架方案执行。

## 1. 交付目标与边界

需要分别回答：

1. 最终部署模型一次推理需要多久，正常负载下波动多大？
2. 新动作发布后，多久第一次被PD控制器采用？
3. 对应电机报文从软件提交到真正发到总线上需要多久？
4. 指令送达后，实际电流何时开始响应、随后上升多快？
5. 策略使用的传感器数据已经有多旧？无法测出的内部采样和滤波时间有哪些？

PD是根据目标角度/速度与反馈误差计算电机指令的控制器。数据龄是“当前使用时刻减该份数据的来源时刻”。抖动是时间的波动，不是传感器数值噪声。

**分三层出结论：**

| 层级 | 能说明什么 | 不能代替什么 |
|---|---|---|
| 测量有效 | 时间定义正确、数据配对完整、原始证据可追溯 | 不代表时延满足控制要求 |
| 时序合格 | 实测结果满足事前确定的周期、截止时间和允许波动 | 不代表机器人行为合格 |
| 行为合格 | 使用该模型、固件和配置的实际行为通过约定验收 | 不替代时序数据和硬件边界核对 |

视频用于行为复核；不能靠视频帧率或肉眼估出微秒级时延。延迟结果只适用于记录的模型、固件、时钟、总线和工况，换模型或改变调度后应重新验证。

## 3. 测点定义：先定起止，再测数值

### 3.1 统一事件表

所有H7软件测点优先使用同一个 `Mono_Ns_Get()` 时钟。外部仪器另有时钟，须经同步后才能相减。

| 时间字段 | 精确定义 | 证据来源 |
|---|---|---|
| `t_sensor_sample` | 传感器真正采样的时刻 | 传感器硬件同步/可信内部时间戳；没有则留空 |
| `t_rx` | H7观察到对应反馈帧的时刻 | 记录是在硬件接收、IRQ入口还是解析完成，三者不能混称 |
| `t_obs_read` | 策略读取该份观测缓存的时刻 | 保存真正读取的缓存序号及各传感来源序号 |
| `t_nn_begin/end` | 网络SDK调用前/后 | 对同一次成功调用配对；失败或未运行另列 |
| `t_action_publish` | 新动作完整发布并可被执行任务读取 | 动作序号与时间在同一发布操作中记录 |
| `t_first_pd_use` | PD第一次实际用到这条动作的时刻 | 动作序号、控制拍序号、许可/门控状态 |
| `t_enqueue_begin/end` | 对应CAN报文提交函数的调用前/返回后 | 每条报文记录总线、CAN ID、返回值及本地发送序号 |
| `t_bus_sof/eof` | 对应CAN帧在线路上开始/结束 | 同步总线波形/分析仪；必须注明实际测的是SOF还是EOF |
| `t_tx_observed` | 软件IRQ或轮询得知CAN已完成的时刻 | 只能称软件完成观察，不能替代精确EOF |
| `t_current_onset` | 实测电流按事前规则首次明显响应的时刻 | 电流探头/驱动内部可验证数据，并与命令同步 |
| `t_current_10/90` | 电流达到本次变化量10%/90%的时刻 | 同一阶跃记录，用于描述响应上升过程 |

电机驱动若提供可信的“收到命令/开始更新电流目标”内部时间戳，可增加对应事件；没有就标“不可直接测量”，不得以HAL成功、CAN ACK或位置变化冒充。

CAN发送事件的时间戳可能对应帧开始；IRQ到达时间又晚于硬件事件。使用前须核对具体芯片参考手册和HAL版本，不凭事件名称猜测时间含义。

### 3.2 计算口径

| 指标 | 计算 | 解释 |
|---|---|---|
| SDK调用耗时 | `t_nn_end - t_nn_begin` | 实际经过时间可能包含中断抢占，不称纯计算周期 |
| 观测读取到动作发布 | `t_action_publish - t_obs_read` | 包含构建、推理和发布；不能再加一次SDK耗时 |
| 动作等待 | `t_first_pd_use - t_action_publish` | 仅首次采用；后续复用计算“动作年龄”，另行统计 |
| CAN提交函数耗时 | `t_enqueue_end - t_enqueue_begin` | 不是CAN报文传输时间 |
| 提交到总线开始 | `t_bus_sof - t_enqueue_begin` | 包含提交处理和硬件排队/仲裁，不称纯队列等待 |
| 线路发送时间 | `t_bus_eof - t_bus_sof` | 由对应真实帧测得 |
| 报文到电流响应 | `t_current_onset - t_bus_eof` | 指定阈值下的电流响应滞后，不自动等于驱动内部纯处理延迟 |
| 电流上升时间 | `t_current_90 - t_current_10` | 表示响应逐渐变化的速度，不是固定等待时间 |
| 可观测端到端响应 | `t_current_onset - t_obs_read` | 必须属于同一动作链且时钟已对齐；不包含未知的传感器内部延迟 |
| H7接收到策略使用的数据龄 | `t_obs_read - t_rx` | 每种传感来源单独统计，不是传感器完整采样延迟 |

硬件可能在HAL函数返回前已开始发送，所以 `t_bus_sof < t_enqueue_end` 不一定是错误。若只有调用前后时间，真实入队时刻在二者之间，不能精确拆出纯队列等待；应报告综合耗时或明确的区间。

**不重复计时：** 控制周期不是额外延迟；相互包含的环节不能重复相加；不同样本的最大值之和不是测得的最大总延迟。

### 3.3 配对规则

复用已有编号；不足时只补必要测点，不新建一套控制框架。分析层至少能还原：

- 会话/板端启动标识、重置次数、观测缓存序号、动作序号、控制拍序号。
- CAN发送尝试序号、总线、CAN ID、硬件buffer编号、成功/失败/取消/重试。
- 电机名称或报文槽位；一条报文可能控制多个电机，不假定“一动作=一CAN帧”。
- 模式、是否允许出力、是否处于保持/故障/切换阶段。

动作序号即使动作值相同也应区分。硬件buffer会复用，不能只靠buffer编号配对；不要为加测量序号修改电机协议内容。

配对在同一启动/重置区间、同一动作链内完成。不跨缺号、断连、复位或故障拼接。找不到唯一对应关系就输出缺测及原因，不能用最近时间的另一条记录替代。

## 5. 一套可实施的示例方案

以下是**示例起点**。实施人须先填写实际板型、网络、调度、总线和动力限值，再判断是否适用。

### 5.1 示例配置

| 项目 | 示例 | 实施前需要确认 |
|---|---|---|
| 策略/PD目标周期 | 10 ms / 2 ms | 实际固件宏和调度；旧50 Hz策略不能冒充100 Hz测试 |
| 时基 | H7单调计时＋外部仪器 | CPU频率、分辨率、回绕、复位边界与同步误差 |
| 软件采集 | 每工况3次，每次60秒 | 缓冲/导出吞吐；正常连续区间每项至少1000个有效配对样本 |
| 预热 | 前5秒单列 | 开始前声明；原始预热数据、丢弃与异常不得删除 |
| 总线采样 | 采样率先按最高位率至少10倍选取 | 实际CAN/CAN-FD位率、仪器解码能力和收发器电平 |
| 电流采样 | 例如100 kS/s | 传感器带宽、噪声、采样分辨率是否足以分辨目标时延 |
| 动力测试 | 单电机、低幅正负阶跃 | 幅值、电流/力矩/角度/速度/温度上限、负载与保护，由台架负责人填写；无通用默认值 |

不用未确认的GPIO脚号或电流值启动测试。示波器/分析仪须使用适合CAN电平的接口；动力阶段固定机构、限制输出、验证急停，不能为测量关闭原保护。

### 5.2 分阶段执行

| 阶段 | 操作 | 产物 | 通过后才能做什么 |
|---|---|---|---|
| A：身份与边界 | 确认实际固件/模型；把每个测点标到代码；填写限值、时钟和接线 | manifest、测点表、limits、接线图 | 有明确版本与测量边界后，进入采集准备 |
| B：时钟与开销 | GPIO同步标记；核对计时器；相同负载下比较采集关闭/开启 | 同步原始波形、转换参数、留出同步点误差、开销报告 | 分辨率和采集影响满足预设要求后开始正式录制 |
| C：软件链路 | 在不产生实际动力输出的条件下运行最终网络，记录读观测、推理、发布、首次PD使用；记录实际门控状态 | 连续原始事件、成功/未运行/失败分类 | 只有真正执行的阶段才有有效样本；未执行的PD/CAN不可记为0耗时 |
| D：CAN链路 | 在已确认的测试模式下发送实际协议报文，同步采GPIO与总线；分别测正常业务负载和允许的较高负载 | 每总线/ID的入队、帧起止、重试与缺测记录 | 对应帧可唯一配对后，形成CAN时序结论 |
| E：单电机响应 | 先隔离单电机，给小幅可辨认指令变化，记录真实电流；左右轮与腿电机分开 | 指令、CAN、电流、状态和每次触发记录 | 只在本机动力限值和保护已确认后执行 |
| F：正常工作负载 | 使用最终模型、真实调度、实际遥测与总线负载重复录制；保留启动/正常/故障分组 | 与部署相符的完整会话 | 不能用无负载微基准直接替代此结果 |
| G：离线复核 | 解码、配对、计算统计、追查极值、独立复算 | D5～D7 | 明确通过/失败/部分有效/未验证 |
| H：仿真映射 | 用测量结果提出候选，独立样本验证 | D8及接口记录 | 经确认后另行修改仿真或开展训练 |

C阶段如果禁用出力导致执行分支不运行，只能交付推理/发布时序，不能假装测完正常PD与CAN。应在D/F阶段补充真实允许条件下的对应记录。

### 5.3 驱动响应示例

示例波形：零指令1秒 → 小幅正阶跃0.2秒 → 零指令1秒；负方向另测。每个方向先做少量试验确认幅值可辨认，再按事先计划完成例如10次独立触发。幅值、保持时间、负载和间隔均由实际设备验证，不能直接照搬其他机器的台架参数。

响应识别规则应在采集前写入配置。例如：

1. 用阶跃前稳定片段计算电流基线与噪声标准差。
2. 示例起变阈值取“3倍噪声标准差”和“平台变化量2%”中较大者，连续3个采样满足才识别，记录第一个满足点。
3. 阈值若已高于平台变化量的10%，或没有稳定平台/发生饱和，标记本次起变时间不可可靠识别，不强算延迟。
4. 同时记录10%～90%上升时间、正负方向和负载，区分等待与逐渐响应。

这是**按阈值定义的电流响应测量**，不是直接看到驱动内部处理时刻。仅有CAN反馈电流时，还包含反馈采样/排队/上传等待；仅有转速时，还包含机械惯性与摩擦。两种情况均须在报告名称与不确定度中说明。

### 5.4 传感器内部延迟如何处理

优先读取可信采样时间戳或数据就绪信号，并对齐到公共时钟。只有H7接收时间时，先交付“接收到策略/PD使用的数据龄”，内部采样与滤波延迟写“未测”。

需要辨识内部滤波滞后时，另做与独立同步参考传感器/编码器的动态对照，记录激励频率和滤波设置；不能仅凭接收频率估算固定延迟，也不能把频率相关的相位变化随意压成一个常数。

## 6. 原始数据与时钟要求

### 6.1 记录字段

优先保留既有原始协议，解码到下列分析含义；不是要求直接重写全部线上报文：

~~~text
session_id,boot_id,reset_count,event_id,event_kind,clock_id,timestamp_raw,
timestamp_unit,observation_seq,action_seq,control_seq,tx_seq,
can_bus,can_id,motor_or_slot,status,mode,output_allowed,source_record_offset
~~~

字段不适用留空；未知时间不能填0。另保留原始报文/波形、固件累计丢弃数、CRC结果、重连、发送失败/取消/重试和记录队列高水位。

分析表按用途分开：

- `actions.csv`：每个唯一动作一次，避免因六电机下发把推理样本重复计六次。
- `transmissions.csv`：每次真实报文尝试，含对应动作/控制拍和实际发送观察。
- `responses.csv`：每次电机阶跃，含电流起变规则、幅值、方向、负载及识别状态。
- `excluded.csv`：所有未配对/无效/被保护中止的记录及原因。

### 6.2 跨时钟校准

H7日志与外部仪器不能直接按各自“时间零点”相减。用多次GPIO边沿建立对应关系，必要时拟合 `t_external = a × t_h7 + b`；开头、中间、末尾均有同步点，并留出未参与拟合的点验证误差。

交付时钟频率/换算、同步边沿位置、拟合参数、留出误差和允许上限。未完成同步时，只报告各自时钟内部的差值，不拼端到端延迟。样本误差低于仪器分辨率时，只能报区间/上界，不能输出虚假的小数精度。

### 6.3 采集开销

在同一固件逻辑、模型、任务负载和总线工况下比较采集关闭/开启，观察控制周期、任务耗时、溢出和丢弃。实时任务只写定长缓冲，后台导出，避免逐帧printf；不通过删除慢样本或降低真实控制频率改善统计。

示例开销目标可以设为“新增执行耗时不超过控制周期1%，且无新增超期/采集丢弃”，但必须由负责人根据实机预先确认，不能当作所有H7的通用验收值。

## 7. 可复现的计算示例

下表**完全是合成数字，不是机器人实测结果**，仅演示同一动作、同一报文、同一已同步时钟的计算。单位为微秒：

| 事件 | 时间 |
|---|---:|
| 观测读取 | 0 |
| 网络调用开始 / 结束 | 20 / 720 |
| 动作发布 | 800 |
| 首次PD采用 | 2000 |
| CAN提交调用开始 / 返回 | 2040 / 2050 |
| CAN帧开始 / 结束 | 2100 / 2230 |
| 电流起变 | 2500 |
| 电流达到10% / 90% | 2600 / 3100 |

应得到：

- SDK调用：700 μs。
- 读观测到发布：800 μs，已包含上述700 μs。
- 发布到首次PD：1200 μs。
- CAN提交调用：10 μs；提交开始到总线开始：60 μs；线路发送：130 μs。
- CAN帧结束到电流起变：270 μs；电流10%～90%上升：500 μs。
- 读观测到电流起变：2500 μs，即2.5 ms。

相邻非重叠区间核对：`800 + 1200 + 40 + 190 + 270 = 2500 μs`。这里40是首次PD到提交起点，190是提交起点到CAN帧结束。不能再把700 μs推理、10 μs提交调用或500 μs上升时间叠加进去。

若工具得到别的数值，先检查单位、事件定义和重复计时。合成数据必须标记 `data_kind=synthetic`，禁止混入实测统计。

## 8. 复现流程与实际命令

### 8.1 收件人复现顺序

1. 核对 `SHA256SUMS`、manifest及板上版本证据，确认数据属于被测模型。
2. 按交付的环境/依赖版本准备离线环境；本仓使用 `mjlab_training/.venv/bin/python`，不混入Isaac旧环境。
3. 先运行合成边界检查，再把原始数据解码到新目录。
4. 使用交付方的实际配对/同步/统计脚本重新生成CSV和报告。
5. 核对有效/无效/缺测数量、每项极值位置、统计口径和误差容限。
6. 在相同设备/版本/负载下重复采集，保留新会话；不能要求随机时序逐条相同，而应按预先规定的重复性范围比较。

### 8.2 已存在工具的离线命令

以下在仓库根目录执行；输出路径须替换成**新的不存在目录**，输入必须是兼容的真实会话。它们不打开串口、不烧录、不使能电机。

~~~bash
PYTHONPATH=mjlab_training/src mjlab_training/.venv/bin/python -m scripts.agent.real2sim.check_h7_latency_capture --out "artifacts/<新软件检查目录>"
mjlab_training/.venv/bin/python sim2sim/h7_latency_capture.py --session "<原始H7会话目录>" --out "artifacts/<新解码目录>"
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 mjlab_training/.venv/bin/python -m scripts.agent.real2sim.analyze_h7_latency --selfcheck
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 mjlab_training/.venv/bin/python -m scripts.agent.real2sim.analyze_h7_latency --session "<本次兼容会话目录>" --out "artifacts/<新统计目录>"
~~~

上面尖括号是必须替换的占位符，不可原样运行。现有分析器覆盖范围见源码；**它不会凭空获得外部电流或总线电气终点**。新增仪器数据的同步、配对和响应分析工具，需要由本次交付方实际实现并随D5提供，不能把计划脚本名写成“已运行”。

板端采集、示波器配置、固件构建/下载的实际命令必须写入交付包 `commands.md`，注明在哪台主机、哪个目录执行、工具版本和真实退出码。本文不提供未经核对的串口名、烧录器参数或动力触发命令。

### 8.3 配对工具必须覆盖的合成检查

| 输入情形 | 必须得到的结果 |
|---|---|
| 同一动作被PD使用多次 | 第一次使用只计一次，后续标为复用 |
| 动作值相同但序号不同 | 不合并为同一个动作 |
| 复位/重启、序号回绕、硬件buffer复用 | 按实际定义分段/展开，不跨边界错配 |
| 丢包、CRC错误、取消/发送失败、SDK失败 | 保留原始记录，相关延迟标缺测或失败，不填0 |
| 未同步的H7/仪器时间 | 拒绝计算跨时钟差值 |
| 总线发送早于HAL返回 | 按测点含义处理，不误判所有此类样本为负延迟 |
| 没有电流阶跃或信噪比不足 | 响应时刻不可识别，不伪造驱动延迟 |
| 故意混入错误模型/会话/采集格式 | 拒绝作为同一份正式结果使用 |
| 本文合成时间表 | 算出第7节的结果，并明确标为合成数据 |

### 9.1 先锁定验收限值

采集前在 `limits.json` 填写负责人、依据、版本和以下字段；未填写的项目不能报告“时序合格”。

~~~json
{
  "status": "example_not_validated",
  "policy_period_us": 10000,
  "pd_period_us": 2000,
  "clock_sync_error_limit_us": null,
  "measurement_overhead_limit_us": null,
  "policy_job_deadline_us": null,
  "pd_job_deadline_us": null,
  "publish_to_first_pd_limit_us": null,
  "publish_to_current_response_limit_us": null,
  "cross_run_repeatability_rule": null,
  "safe_step_amplitude": null,
  "safe_step_unit": null,
  "hardware_owner": null,
  "limits_confirmed_before_capture": false
}
~~~

10000/2000只是本任务的示例目标周期，须核对板上实际配置。截止时间应由具体调度和控制要求确定；没有依据时只出测量报告，不任意设一个“通过线”。

### 9.2 按关卡验收

| 关卡 | 检查方法 | 通过标准 | 不通过时 |
|---|---|---|---|
| G1：身份与原始证据 | 核对模型/固件/源码/设置/原始文件哈希 | 测试版本可追溯，关键字段完整 | 不使用不明版本推断当前模型性能 |
| G2：测量可信度 | 时钟校准、留出点、采集开销对照、仪器分辨率核对 | 满足事先锁定的误差和开销界限 | 修正测量链路，另存新采集 |
| G3：数据完整性 | 核对序号、CRC、丢弃、头尾、模式与配对数量 | 声称完整的连续区间无未解释缺口；每个纳入统计的样本唯一配对 | 全文件失败如实保留，可单列有效区间，但不得改称全文件完整 |
| G4：离线可复算 | 新目录重跑解码/配对/统计，抽查样本与全部极值 | 原始索引与计数一致；数值差在声明容差内 | 修复工具/单位/时钟问题，不能只改报告 |
| G5：时序性能 | 按模型、阶段、电机、总线和负载分组对照limits | 所有被要求的硬截止项目均满足；百分位项目按事前规则满足 | 报告超期次数和比例；不能拿P99通过掩盖硬截止违例 |
| G6：重复性与交接 | 重复运行、留出会话及另一位复核者核对 | 满足事先规定的重复性范围，结论适用边界清楚 | 标记不稳定或部分有效，不写“已适配实机” |

P95/P99表示95%/99%的**已观察样本**不超过的值，不是未来最坏情况保证。每组至少报告总数、有效数、缺测数及原因；标准差注明采用总体标准差，分位数算法注明，例如线性插值，避免工具默认口径不同。

启动、正常运行、后台高负载、故障/恢复、禁用分别统计。预热和异常不能从原始文件删除；慢样本不能因为“看起来不正常”就从正常工况统计中任意剔除。

## 10. 如何交给训练侧使用

1. 先确定仿真里的“延迟”从哪个事件开始、到哪个事件结束，再选择对应实测量。例如动作发布到首次PD，与观测读取到首次PD不是同一指标。
2. 按同一动作链的实际总差值统计，不把各环节P99/最大值相加。不要把控制周期、已有动作等待和推理耗时重复加入。
3. 动作等待、传感器数据龄、电流响应动态分开建模。响应时间常数不是固定死区；仅有CAN反馈或转速测量时不能假装已分离纯驱动延迟。
4. 将实测值映射到2ms仿真网格时，明确取整规则、误差和未解析的抖动；不能静默四舍五入后称逐点对齐。
5. 先形成独立候选文件，记录数据来源、模型/固件哈希、单位、各电机范围、异常处理和未知项。缺测使用空值/未测标志，不填0。
6. 用未参与选参数的会话验证候选，再按新预算做仿真行为对照。本文不自动修改现有零额外延迟设置、不授权重训。
